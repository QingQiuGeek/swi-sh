# 保单托管 / 保单诊断 / 保单优化 与线索 Pipeline 方案

> **本文是方案文档，不是已实现功能。** 落地方案里每一条都标注了「现在能不能做、依赖什么」。
> 相关既有文档：`PROJECT-NOTES.md`（工程实现）、`docs/prd.md`（当前范围）、`docs/page-specs.md`（页面结构）、`docs/avoid.md`（不要做什么）。

## 0. 先对齐三件事

### 0.1 目标口径

这三个页面**不是**"提高投保转化率"，而是**把匿名流量变成可跟进的实名线索**。

| 层次     | 指标                                     | 本项目现在有没有                                                |
| -------- | ---------------------------------------- | --------------------------------------------------------------- |
| 流量     | 访问量 / 停留                            | 无埋点，看不到                                                  |
| 留资     | 手机号 + 车辆信息                        | **只有提交投保那一刻才有**（本节 0.3 会说明为什么这是致命缺口） |
| 线索质量 | 车辆信息完整度、现保单到期时间、诊断结论 | 无                                                              |
| 转化     | 报价 → 成交                              | 有订单模型                                                      |

所以要做的第一件事不是"加三个页面"，而是**在投保之前**插入低门槛的留资节点。

### 0.2 三个概念的边界

| 概念                               | 输入                                                               | 输出                                                       | 依赖真实业务到什么程度                                                       |
| ---------------------------------- | ------------------------------------------------------------------ | ---------------------------------------------------------- | ---------------------------------------------------------------------------- |
| **保单托管** `Policy Custody`      | 用户手动录入的既有保单要素（保险公司、险种、保额、起止日期、保费） | 一张"我的保单"清单 + 到期日历 + 缺口视图                   | **低**。纯结构化存储 + 计算，本项目可以完全做实                              |
| **保单诊断** `Policy Checkup`      | 问卷答案 + 托管里的保单 + 车辆信息                                 | 结构化诊断报告：覆盖缺口、保额是否充足、期限状态、保费水位 | **中**。缺口判断用规则引擎即可；"保费是否买贵了"需要真实费率库，只能给区间   |
| **保单优化** `Policy Optimization` | 诊断结果                                                           | 2–3 档方案（保守补足 / 均衡 / 高保障）+ 预估保费           | **中高**。方案可以基于站内产品生成，但"更优"的结论需要承保规则与核保结论支撑 |

一句话：**托管是数据、诊断是规则、优化是建议**。三者串起来才是一条完整的产品线，单独做一个都不成立。

### 0.3 三条硬约束（先说清楚，否则方案会飘）

1. **没有真实保单数据源。** 本项目没有保险公司 API、没有中保信对接、没有 OCR。所以"托管"只能从**用户手动录入**起步（§2.3 给了取舍）。
2. **注册只要邮箱，不要手机号。** 现在 `lib/server/auth.ts` 的注册表单只有 `username` / `email` / `password`。**没有手机号的线索，业务方打不了电话**——这是整个方案里最需要先改的一件事。
3. **当前是演示站，PII 是明文存的。** 投保表单收的身份证号、车架号直接进 Redis（`swi:order:{id}`），既没有加密也没有留存期限。**要做线索沉淀，合规改造必须先于功能上线**（§9）。

## 2. 有哪些可以做（按性价比排序）

### 2.1 四条产品线

| #   | 产品线                            | 免登录    | 直接收线索             | 成本         | 优先级 |
| --- | --------------------------------- | --------- | ---------------------- | ------------ | ------ |
| A   | **保单体检**（问卷 → 诊断报告）   | ✅        | ✅ 强                  | 中           | **P0** |
| B   | **报价试算**（车况 → 3 秒出价）   | ✅        | ✅ 强                  | 低           | **P0** |
| C   | **保单托管**（保单夹 + 到期日历） | ❌ 需登录 | ❌ 间接（靠 A/B 导流） | 中           | P1     |
| D   | **续保提醒**（到期前触达）        | ❌        | ✅ 最强（时机型）      | 低（依赖 C） | P1     |

为什么 A 和 B 排在最前：它们是**唯一能在"用户还没打算买"的阶段拿到手机号**的入口。C 和 D 是留存与时机放大器，靠 A/B 的线索导流才有量。

### 2.2 围绕主线的辅助能力（都是为线索服务的）

- **线索事件流与归因**：任何线索都要能回答"从哪来、看了什么、卡在哪一步"。（§4.4）
- **线索评分与分档**：A/B/C 三档，供业务按优先级跟进。（§4.5）
- **销售侧只读列表**：一个内部页面，能看、能筛选、能改跟进状态。**不做 CRM**，够用即可。（§5）
- **AI 前置问答**：复用现有 `ServiceChat`，把"我该买什么"这类开放问题引流到体检问卷。（§7）
- **分享裂变**：诊断报告生成一张可分享的结果卡（不泄露个人信息），带回新流量。
- **续保卡片**：保单到期前在个人中心与 AI 客服里主动提示。

### 2.3 「托管」的录入方式怎么选（需要拍板）

| 方案                       | 可行性                      | 体验                      | 建议                                                         |
| -------------------------- | --------------------------- | ------------------------- | ------------------------------------------------------------ |
| 手动逐字段录入             | 现在就能做                  | 差（一份保单约 8 个字段） | **P0 起步**，配向导 + 只问必需项                             |
| 上传保单照片 + OCR         | 需要接入 OCR 服务，本项目无 | 好                        | P2，明确列为外部依赖                                         |
| 保险公司 / 中保信 API 对接 | 需要商务与资质              | 最好                      | 不在本项目范围                                               |
| 从订单自动生成             | 已有订单可一键转成保单      | 极好                      | **P0**：买了站内产品的用户，订单直接进保单夹，托管量立刻有底 |

**推荐组合：站内订单自动入夹（零成本拿到存量）+ 手动录入向导（增量）+ OCR 作为后续依赖。**

## 3. 引导交互怎么做（本方案的重点）

### 3.1 通用漏斗骨架：五段式

```
① 匿名进入        ② 逐步问卷           ③ 免费摘要           ④ 注册墙             ⑤ 完整报告 + 留资
[低门槛入口]  →  [一屏 1–2 题]  →  [先给一个确定性]  →  [价值最高点]  →  [保存 / 约顾问]
   无表单          进度条可见          "你的保单有 2 处缺口"     弹登录框           手机号 + 到店/回电意愿
```

关键点：**注册墙不放在入口，放在"结果已经生成、但还没解锁"的位置。** 用户已经投入了 6–8 个问题的时间，此时注册的转化率远高于一进门就要求注册；而且我们在他注册前就已经拿到了问卷答案（`sessionId` + 匿名 token），注册只是**把匿名线索合并到账号上**，不损失信息。

### 3.2 保单体检：分步问卷设计

| 步  | 只问什么                                                     | 为什么这一步问                                               | 产出     |
| --- | ------------------------------------------------------------ | ------------------------------------------------------------ | -------- |
| 1   | 车牌归属地（省份即可）                                       | 定位费率区，可跳过                                           | 区域     |
| 2   | 车辆：品牌型号 / 注册年份                                    | 车价与车龄是保费主因                                         | 车辆档位 |
| 3   | 现在有保单吗？                                               | **分叉点**：有 → 走录入；无（裸奔 / 只有交强险）→ 走缺口诊断 | 分叉     |
| 4   | 现有险种勾选（交强 / 三者 / 车损 / 座位 / 不计免赔 / 划痕…） | 缺口判定的核心输入                                           | 险种集合 |
| 5   | 三者保额、车损保额                                           | 保额是否充足                                                 | 保额     |
| 6   | 保费大概多少（三档区间，允许"不清楚"）                       | 判断保费水位                                                 | 保费档   |
| 7   | 保单到期时间                                                 | **时机型线索的关键**                                         | 到期日   |
| 8   | 平时用车场景（通勤 / 长途 / 营运 / 很少开）                  | 优化建议的分叉                                               | 场景     |
| 9   | 出过险吗                                                     | 影响续保建议                                                 | 出险记录 |
| 10  | 生成报告 → 注册墙 → 手机号（约顾问回电）                     | ④⑤ 两段                                                      | **线索** |

设计要点：

- **每屏 1–2 题**，进度条可见（"第 4 / 10 步"），可回退，可跳过非必需项。
- **允许"不清楚"**：填不出保额的用户占多数，硬性要求会直接掉一半人。缺失项在报告里标成"待补充"，反而成为**回访理由**。
- **第 3 步是最关键的分叉**：没有保单的用户是"新增投保线索"，有保单的是"优化 / 续保线索"，两条后续话术与跟进 SLA 完全不同。
- 问卷答案**在注册前就落库**（匿名 token），这样即使他没注册，也是一条可分析的线索。

### 3.3 保单诊断报告生成什么

报告分"免费摘要"与"完整版"两层，这是注册墙两侧的内容分界：

| 区块               | 免费摘要（注册前）              | 完整版（注册后）                 |
| ------------------ | ------------------------------- | -------------------------------- |
| 覆盖缺口           | "检出 2 处缺口"（不说是哪两处） | 逐项列出缺口 + 缺口说明          |
| 保额充足度         | 只给结论："三者保额偏低"        | 给出建议区间 + 依据              |
| 保费水位           | 隐藏                            | 与同车型区间的对比（注明为估算） |
| 期限状态           | "有 1 项即将到期"               | 到期日 + 提前续保时间窗          |
| 优化方案           | 隐藏                            | 2–3 档方案 + 预估保费 + 一键投保 |
| 保存 / 导出 / 回访 | 隐藏                            | 保存到保单夹、留下手机号约顾问   |

**"检出 N 处缺口"这个设计是刻意的**：给确定性、制造好奇、但不给完 —— 这是注册墙能起作用的唯一理由。不做"什么都藏"，也不做"什么都给"。

### 3.4 保单优化：怎么给出"更优"

| 档位     | 逻辑                             | 对应站内产品                       |
| -------- | -------------------------------- | ---------------------------------- |
| 保守补足 | 只补真实缺口，控制预算           | 单险种（`category: single`）       |
| 均衡推荐 | 三者 + 车损 + 座位，配齐主要风险 | 商业险套餐（`commercial-package`） |
| 高保障   | 提高三者保额 + 全年救援          | 高配套餐（如畅行版档位）           |

三条硬规则：

1. **方案必须给出"为什么"**（缺了什么 → 补上它解决什么），不能只列商品。
2. **不能出现绝对化用语**：不许写"最划算""保证理赔""全市场最低"（`广告法` 明令 + `docs/avoid.md` 的内容口径）。
3. **每个结论必须可回溯**：存问卷输入 + 规则版本号 + 生成结论，出问题能复盘（§9.3）。

### 3.5 报价试算：3 秒出价怎么做

用现有产品价格 + 车辆系数即可，**不需要真实费率**：

```
预估年保费 = 产品基准价 × 车龄系数 × 险种系数 × 出险系数
```

- 车龄系数：`<=3年 1.0 / 4–8年 1.15 / >8年 1.35`
- 出险系数：`无出险 0.85 / 1次 1.0 / 2次以上 1.3`
- **必须在结果页显著标注"预估值，实际保费以核保结论为准"**，否则就是误导。

锁价动作（"把报价发给顾问 / 保存这版报价"）就是留手机号的钩子。

### 3.6 复用的现有代码资产

| 现有能力                                 | 位置                                                    | 怎么复用                                                                             |
| ---------------------------------------- | ------------------------------------------------------- | ------------------------------------------------------------------------------------ |

## 4. 数据模型

### 4.1 新增领域模型（放 `lib/types/index.ts`）

### 4.2 Redis 键设计（沿用 `lib/server/redis.ts` 的 `redisKeys` 约定）

现有前缀统一 `swi:`，新增键全部集中进同一个对象，读写两侧不拼错：

| 键                        | 值                                          | TTL       | 用途                                        |
| ------------------------- | ------------------------------------------- | --------- | ------------------------------------------- |
| `swi:lead:{leadId}`       | `Lead`                                      | 无        | 线索本体                                    |
| `swi:leadbyphone:{phone}` | leadId                                      | 无        | **手机号唯一索引**，身份合并用              |
| `swi:leadbyanon:{anonId}` | leadId                                      | **30 天** | 匿名 token → 线索                           |
| `swi:leads:{stage}`       | List of leadId                              | 无        | 按阶段的列表，销售侧筛选用                  |
| `swi:uleadof:{userId}`    | leadId                                      | 无        | 用户 → 线索（一人一条，合并后保留最早那条） |
| `swi:leadevent:{leadId}`  | List（append-only）                         | 无        | 事件流，见 §4.4                             |
| `swi:checkup:{checkupId}` | `Checkup`（问卷答案 + 报告快照 + 规则版本） | **1 年**  | 诊断记录                                    |
| `swi:poly:{policyId}`     | `Policy`                                    | 无        | 保单                                        |
| `swi:upolys:{userId}`     | Set of policyId                             | 无        | 用户保单集合                                |
| `swi:leadnote:{leadId}`   | List                                        | 无        | 人工跟进记录                                |

两个与现有设计一致的决定：

- **列表与索引分开存**（`lead:{id}` + `leads:{stage}` + `leadbyphone:{phone}`），和现在 `order` / `uorders` / `dedup` 是同一套路数。
- **TTL 只给可再生的数据**：匿名 token 30 天、诊断记录 1 年；线索与事件流不设 TTL（这是要长期沉淀的资产）。

### 4.3 身份合并（这条最容易做错）

线索会以三种身份出现，必须能合并成一条：

```
匿名（anonId）  ──留手机号──▶  线索（phone）  ──注册──▶  绑定（userId）
       │                          │                      │
       └──────── 同一条 leadId，逐级补字段，不新建记录 ─────┘
```

实现规则：

1. **以 leadId 为主键，禁止"注册时新建一条线索"**——那会造成同一人三条记录。
2. 留手机号时：先查 `leadbyphone:{phone}`，命中就把当前 `anonId` 合并进去（保留最早 `createdAt`），未命中才写新索引。
3. 注册成功时：只做 `userId` 回填 + `userId → leadId` 反向索引，**不改 stage 以外的任何业务字段**。
4. 手机号换绑：更新 `leadbyphone` 新旧两个键，避免留下指向错误人的悬挂索引。
5. 手机号统一按纯数字存（去掉空格与 `+86`），与现有 `normalizeEmail` 同一思路。

### 4.4 线索事件流

每个 leadId 下挂一条 append-only 的 List，事件类型：

```
enter_page  →  step_complete(step=4)  →  report_generated  →  gate_shown
→ register_success  →  phone_submitted  →  quote_locked  →  order_created
→ order_paid  →  policy_saved  →  renew_reminder_sent  →  follow_up(note)
```

用途：① 归因与漏斗分析（哪一步掉人最多）；② 业务跟进时看到完整上下文；③ 合规留痕（用户同意了哪一版告知文本、什么时间同意的）。

**事件只追加不修改**，和订单一样保留快照。

### 4.5 线索评分（规则打分，不用 ML）

评分表要**可解释**，业务方能自己改权重：

| 维度       | 取值                   | 分值 |
| ---------- | ---------------------- | ---- |
| 现保单状态 | 无保单                 | +30  |
|            | 只有交强险             | +25  |
|            | 三者保额 < 100 万      | +15  |
|            | 配置齐全               | +5   |
| 到期时间   | 30 天内到期            | +25  |
|            | 90 天内                | +15  |
|            | 无信息                 | 0    |
| 车辆       | 车龄 ≤ 8 年            | +10  |
|            | 出过险                 | +5   |
| 行为       | 已注册                 | +15  |
|            | 已锁定报价             | +20  |
|            | 有站内订单             | +10  |
| 触达意愿   | 主动勾选"希望顾问联系" | +20  |
|            | 明确拒绝联系           | −50  |

`score ≥ 70 → A`、`40–69 → B`、`< 40 → C`。

**这里有一个合规注意点**：给用户打分并据此决定营销优先级，在《个人信息保护法》里属于**自动化决策**（第 24 条），需要做到透明可告知、并给用户拒绝权。落地时至少要在告知文本里写明"我们会根据你填写的信息判断跟进优先级"。

## 5. 线索 Pipeline

| 阶段          | 进入条件（事件）          | 系统自动动作                                      | 负责人 | SLA              |
| ------------- | ------------------------- | ------------------------------------------------- | ------ | ---------------- |
| `ANONYMOUS`   | `enter_page`              | 记录来源与问卷进度                                | —      | —                |
| `CAPTURED`    | `phone_submitted`         | ① 写入唯一索引 ② 按分数分档 ③ 若为 A 档，推送提醒 | 电销   | **2 小时内首触** |
| `REGISTERED`  | `register_success`        | 匿名线索合并到 userId，触发欢迎触达               | 电销   | 24 小时内        |
| `DIAGNOSED`   | `report_generated`        | 生成完整报告，附在跟进详情里                      | 电销   | —                |
| `QUOTED`      | `quote_locked`            | 报价单快照入线索                                  | 电销   | 24 小时内        |
| `CONVERTED`   | `order_paid`              | 订单自动入保单夹，停止推销动作                    | —      | —                |
| `RENEWAL_DUE` | 到期前 45 / 15 / 3 天     | 到期提醒（站内 + AI 客服 + 触达）                 | 电销   | 提前 45 天启动   |
| `LOST`        | 明确拒绝 / 超 30 天未触达 | 归档，90 天后可再营销（需重新取得同意）           | —      | —                |

两个设计原则：

1. **`stage` 是系统判定的，`followUp` 是人改的**，两者分开存。混在一起的结果是：人一改状态，漏斗分析就全乱了。
2. **每个阶段都有明确的进入事件**，没有"手动拖卡片"的空间。Pipeline 的价值在于自动推进，不是给销售一套看板。

## 6. 接口设计

沿用现有信封（`lib/server/api-response.ts`）与业务码机制，新增码进 `API_CODES` 与 `HTTP_STATUS_BY_CODE`：

| 新增业务码           | 含义                      | HTTP |
| -------------------- | ------------------------- | ---- |
| `PHONE_TAKEN`        | 手机号已被其它账号占用    | 409  |
| `LEAD_NOT_FOUND`     | 线索 / 报告不存在或已过期 | 404  |
| `CHECKUP_INCOMPLETE` | 问卷未完成，无法生成报告  | 409  |
| `CONSENT_REQUIRED`   | 未取得同意，拒绝落库      | 403  |

| 方法           | 路径                                 | 鉴权           | 说明                                                |
| -------------- | ------------------------------------ | -------------- | --------------------------------------------------- |
| POST           | `/api/checkups`                      | 否             | 创建诊断（返回 `checkupId` + `anonToken`）          |
| PATCH          | `/api/checkups/[id]`                 | 否             | 逐步提交问卷答案（幂等，可回退）                    |
| POST           | `/api/checkups/[id]/report`          | 否             | 生成报告：返回免费摘要；完整版需登录                |
| POST           | `/api/checkups/[id]/claim`           | 否             | 留手机号 + 同意留痕 → **产生线索**                  |
| POST           | `/api/quotes`                        | 否             | 报价试算，返回区间 + 免责声明文案                   |
| POST           | `/api/quotes/[id]/lock`              | 否             | 锁定报价 → 留手机号                                 |
| GET / POST     | `/api/policies`                      | **是**         | 我的保单列表 / 手动新增                             |
| POST           | `/api/policies/from-order/[orderId]` | **是**         | 订单一键转保单                                      |
| PATCH / DELETE | `/api/policies/[id]`                 | **是**         | 修改 / 删除保单                                     |
| GET            | `/api/leads`                         | **是（内部）** | 销售侧列表，支持 `?stage=` `?grade=` `?owner=` 筛选 |
| PATCH          | `/api/leads/[id]`                    | **是（内部）** | 改跟进状态 / 负责人 / 备注                          |
| GET            | `/api/leads/[id]/events`             | **是（内部）** | 事件流                                              |

**两个必须提前定的事**：

- `/api/leads*` 是**内部接口**，面向销售。现在项目里没有角色体系（`User` 没有 `role` 字段），要么加 `role`，要么用一个独立的内部令牌校验。**建议加 `role`**，因为后面还会需要"管理员看报表"这类能力。
- 「未登录也能调 `/api/checkups/*`」意味着接口要防刷（现在全站没有任何限流）：至少按 IP + 匿名 token 做频次限制，否则会被脚本灌垃圾线索。

## 7. AI 怎么接（复用现有能力）

现有 AI 客服已经具备：`ToolLoopAgent` + zod 工具、`useChat` 流式、会话 7 天留存、登录态绑定（`lib/server/ai/agent.ts`、`tools.ts`）。

### 7.1 推荐做法：结构化问卷为主，AI 做解释与追问

不建议把诊断完全做成对话——问卷能保证数据结构化、可统计、可回溯；对话适合做"解释结论"和"追问缺失项"。两者分工：

| 环节       | 谁做           | 为什么                                                     |
| ---------- | -------------- | ---------------------------------------------------------- |
| 采集信息   | 问卷（结构化） | 字段可控，能进数据库，能算分                               |
| 解释结论   | AI             | "为什么说三者保额偏低"这类问题用自然语言回答最自然         |
| 追问缺失项 | AI             | 用户不知道"三者保额"是什么，让它现场解释                   |
| 生成方案   | **规则引擎**   | 涉及保费与险种组合，必须可回溯、可审计，不能让模型自由发挥 |

### 7.2 新增 AI 工具（草案）

```ts
// 诊断结果解读：只读用户自己的诊断，不返回他人数据
createCheckupExplainTool({ authedUserId, locale });
inputSchema: z.object({
	checkupId: z.string(),
	question: z.string().optional(), // 用户的具体追问
});
// 与 createOrderQueryTool 一样：checkupId 必须属于 authedUserId，否则返回 requiresLogin

// 缺口规则解释：把规则引擎的结论翻译成人话
createCoverageGapExplainTool(locale);
inputSchema: z.object({ gaps: z.array(z.string()) });

// 优化方案查询：只返回规则引擎算好的档位，模型不得自创价格与险种
createOptimizationPlanTool({ locale });
inputSchema: z.object({
	checkupId: z.string(),
	tier: z.enum(['basic', 'balanced', 'premium']),
});
```

**延续现有安全做法**：所有涉及个人数据的工具，都必须把服务端解析出的 `userId` 与参数里的 id 再比对一次（照抄 `createOrderQueryTool` 的写法），模型无法通过伪造参数读到别人的数据。

### 7.3 三条 AI 使用红线

1. **不得由模型给出价格承诺或"保证赔付"类结论**，价格只来自规则引擎的结果。
2. **AI 生成的内容要标注**（"以下由智能助手生成，仅供参考"），并在用户端可回溯到生成时的输入。
3. **不做自动化核保结论**："你可以投保"这种话必须由规则与后续核保决定，不能由对话模型说。

## 9. 合规与数据安全（必须做，不是可选项）

这一节是这个方案里**风险最高的部分**，务必先过法务/合规再开发。

### 9.1 个人信息保护（PIPL）

| 要求         | 现在缺什么                                   | 要做什么                                                            |
| ------------ | -------------------------------------------- | ------------------------------------------------------------------- |
| 告知同意     | 注册只有基础的隐私政策链接，留资没有单独同意 | 留手机号前弹**独立同意勾选框**，记录 `consentAt` + `consentVersion` |
| 敏感个人信息 | 身份证号、车架号**明文**存在 Redis           | 单独同意 + 字段级加密（至少应用层加密），访问审计                   |
| 最小化       | 投保表单一次要 6 个字段                      | 体检问卷只问诊断必需的，身份证等敏感项不到投保环节不收              |
| 留存期限     | 订单、保单**无期限**                         | 定义各表保留期（如诊断记录 1 年、线索 2 年），到期清理或匿名化      |
| 撤回与删除   | 无                                           | 个人中心提供"撤回同意"与"删除我的诊断/保单"入口                     |
| 自动化决策   | 无                                           | 线索评分要可告知、给拒绝权（§4.5）                                  |
| 第三方共享   | 无                                           | 若要转给保险公司/代理人，需**单独同意**并记录接收方                 |

### 9.2 保险销售合规

- **不得使用绝对化用语**："最便宜""全网最低""保证理赔""稳赚"——`广告法` + 保险监管口径都禁止。这条要写进 `docs/avoid.md`。
- **必须显著免责**：报价与优化建议都要标注"仅供参考 / 预估，实际以核保结论与条款为准"。
- **销售过程可回溯**：谁在什么时间看到/听到什么建议，要留痕（诊断输入 + 规则版本 + 输出）。
- **不承诺承保**：体检报告不得写"你一定能投保"。

### 9.3 可回溯实现方式

每条诊断记录存：`规则版本号` + `问卷原始答案` + `生成的结论快照`。规则改版后，旧报告仍能解释"当时为什么这么判"。

### 9.4 现状提醒

现在的演示站是**明文 PII + 无同意留痕 + 无限流 + 无角色权限**。做线索沉淀等于把这些短板全部暴露在真实流量下。**§9 的改造要先于功能上线**，不是"以后再说"。

## 11. 需要业务方拍板的问题

1. **注册是否加手机号？** 不加，就只能在体检/报价链路里收（本方案按"不加"设计，但那样线索质量与去重能力都受限于体检链路）。
2. **「更优」怎么定义？** 是"更便宜"还是"保障更全"？这决定了优化建议的话术与产品排序逻辑。**这是最影响方案走向的一个问题。**
3. **费率区间从哪来？** 没有真实费率库，"保费水位"只能标成估算，业务方能否接受？
4. **线索给谁？** 自建电销 / 转给保险公司 / 转给代理？直接决定是否需要第三方共享同意（§9.1）。
5. **留资的同意文案由谁出？** 必须合规出稿，不能由开发自己写。
6. **保单数据谁负责准确性？** 用户手填的保单必然有错，建议谁用谁担，但需明确写入免责。
7. **是否要做内部线索系统？** 还是导出 CSV 给现有 CRM？导出的合规要求（加密传输、接收方资质）不同。
