## 1. 产品定位

一句话：面向个人车主的「车险产品浏览 → 在线投保 → 订单管理」中英双语网站。

**是什么**

- 车险产品的展示型 + 交易型官网：看清楚保什么、多少钱，并在线完成投保下单。
- 自助式个人中心：登录后可查看管理订单、修改资料与密码。
- 产品目的大小：6 款车险产品，覆盖法定险、商业险套餐与单险种。

**不是什么（本期明确不做）**

- 不做真实支付与真实保单出具。
- 不做理赔申请、报案、定损等售后流程。
- 不做保险经纪/运营后台，不做代理人分佣体系。
- 不做真实保险公司/监管系统对接。

**差异化**

- 产品对比清晰：价格、保额、服务内容一眼可比，避免条款黑箱。
- 投保指引完备：材料清单 + 流程步骤 + 常见问题，降低投保门槛。
- 真正的双语体验：中英文对等的页面与数据，URL 明确区分语言，便于分享与收录。

## 2. 目标用户

| 用户群 | 特征 | 核心诉求 | 优先级 |
| --- | --- | --- | --- |
| 个人车主 | 25–45 岁，有车 1–5 年，面临首保或续保 | 快速看懂价格与保障范围，线上完成投保 | 主 |
| 企业车队负责人 | 管理 5 台以上车辆 | 了解车队方案与批量投保流程 | 次 |
| 英文用户 | 在华外籍人士或英文环境访问者 | 用英文完成同等浏览与投保 | 次 |

## 3. 用户问题

1. **看不懂**：车险条款术语密集，「保什么、不保什么」不直观。
2. **比不了**：价格不透明，横向对比多家产品的时间成本高。
3. **不会办**：不清楚投保需要哪些材料、要走几步、要多久。
4. **查不到**：线上提交后，订单状态与凭证无处可查。
5. **语言隔阂**：非中文用户无法获取同等信息。

---

## 4. 核心场景

- **S1 浏览比较**：进入首页 → 滚到「保险产品」分区 → 浏览产品卡片（名称/价格/服务内容）→ 进入产品详情对比。
- **S2 了解流程**：滚到「投保指引」分区 → 查看材料清单与流程步骤 → 返回产品继续投保。
- **S3 在线投保**：产品详情 → 点「立即投保」→ 填写被保人/车辆信息 → 提交 → 生成订单。
- **S4 订单管理**：登录 → 个人中心 → 我的订单 → 查看订单详情 / 取消订单 / 模拟支付。
- **S5 账户维护**：个人中心 → 修改资料 / 修改密码。
- **S6 语言切换**：任意页面切换中/英 → 跳转到同页面的另一种语言 URL，回到同一位置。

## 6. 用户流程

### 6.1 浏览与投保（主流程）

```
首页 Hero（/zh）
  └─ 平滑滚动 → 保险产品分区 → 产品卡片
        └─ 查看详情 → /zh/products/[slug]
              └─ 立即投保
                    ├─ 未登录 → 打开登录/注册弹窗 → 成功后回到投保表单
                    └─ 已登录 → /zh/purchase/[slug] 填写被保人 + 车辆信息 → 提交
                          └─ 生成订单 → 跳转个人中心「我的订单」
```

### 6.2 注册 / 登录

```
点击 Header 右侧「登录/注册」
  └─ 弹窗（登录 | 注册 两个 Tab）
        ├─ 注册：用户名 + 邮箱 + 密码 → 校验 → 自动登录进入个人中心
        └─ 登录：邮箱 + 密码 → 校验 → 关闭弹窗，回到原页面位置
异常：邮箱已注册 / 账号密码错误 / 字段校验失败 → 表单内联错误提示
会话过期（1 小时）：接口返回未授权 → 前端清除登录态 → 唤起登录弹窗 → 登录成功后回到当前页面
```

### 6.3 个人中心

```
Header 右侧用户名 /「个人中心」
  └─ 未登录 → 打开登录弹窗
  └─ 已登录 → /zh/account（左侧边栏 Tab，右侧内容区）
        ├─ 概览：账户信息 + 订单统计 + 快捷入口
        ├─ 我的订单：列表（全部 | 待支付 | 已生效）→ 详情 → 取消订单 / 模拟支付
        ├─ 修改资料：用户名 + 邮箱 → 保存
        └─ 修改密码：当前密码 + 新密码 + 确认新密码 → 保存
```

### 6.4 语言切换

```
点击 Header 右侧「中 / EN」
  └─ 把当前路径的语言段替换为目标语言（/zh/xxx ↔ /en/xxx）并跳转
        ├─ 保持同一页面，不回首页
        ├─ 保持当前位置：把当前所在分区写入 sessionStorage，目标页面读取后复原
        └─ 写入语言 Cookie，下次访问根路径时按此语言跳转
```

## 7. 页面 / 功能列表

**路由形态**：语言作为 URL 第一段（`/zh`、`/en`），根路径 `/` 由中间件按语言偏好重定向。全站使用 App Router 真实路由，不使用 hash 路由。

| Route | 页面 | 需登录 | 主要内容 |
| --- | --- | --- | --- |
| `/` → `/[locale]` | 重定向入口 | 否 | 按 Cookie → `Accept-Language` → 默认 `zh` 重定向 |
| `/zh`、`/en` | 首页（五分区） | 否 | Hero、保险产品、投保指引、投保案例、关于我们 |
| `/[locale]/products` | 产品列表 | 否 | 产品卡片网格、价格、服务内容摘要 |
| `/[locale]/products/[slug]` | 产品详情 | 否 | 保险名、价格、保额、服务内容明细、立即投保 |
| `/[locale]/purchase/[slug]` | 投保表单 | 是 | 被保人信息、车辆信息、费用确认、提交投保 |
| `/[locale]/guide` | 投保指引 | 否 | 流程步骤、材料清单、常见问题 |
| `/[locale]/about` | 关于我们 | 否 | 公司介绍、核心数据、联系方式 |
| `/[locale]/account` | 个人中心 · 概览 | 是 | 左侧边栏 + 账户信息、订单统计 |
| `/[locale]/account/orders` | 个人中心 · 我的订单 | 是 | 订单列表、状态筛选 |
| `/[locale]/account/orders/[id]` | 个人中心 · 订单详情 | 是 | 订单号、产品、被保人、车辆、金额、状态、取消、模拟支付 |
| `/[locale]/account/profile` | 个人中心 · 修改资料 | 是 | 用户名、邮箱 |
| `/[locale]/account/password` | 个人中心 · 修改密码 | 是 | 当前密码、新密码、确认新密码 |
| `not-found` | 404 | 否 | 双语 404 页面；非法语言段同样走 404 |

**个人中心布局**：桌面端为「左侧边栏 Tab + 右侧内容区」，四个 Tab 顺序固定为 概览 / 我的订单 / 修改资料 / 修改密码；移动端降级为顶部横向可滚动 Tab。Tab 间切换使用客户端导航，不整页刷新。

**全局组件**

- **Header**（吸顶）：左侧「汽车保险」+ Logo（`public/next.svg`）；中间导航 Tab：首页 / 保险产品 / 投保指引 / 投保案例 / 关于我们；右侧语言切换（中/EN）+ 登录注册按钮（已登录时显示用户名与个人中心入口）。
- **Footer**：四栏——品牌简介 / 导航链接 / 联系方式（地址、电话、邮箱，全部 mock）/ 微信客服（二维码 + 提示文案）；底栏为备案号（mock）+ 版权 + 演示数据声明。联系方式中的电话与邮箱是可点击链接（`tel:` / `mailto:`）。**页脚不提供语言切换**，语言入口只在 Header。
- **首页悬浮工具轨**（`FloatingTools`）：仅首页、仅 xl（≥ 1280px）显示，视口右侧垂直居中；三项——在线客服（点击在按钮左侧弹出 Popover，内嵌 AI 客服对话，见 §10.4）、联系方式（悬浮提示框：电话 / 邮箱 / 微信二维码）、返回顶部（平滑滚动回顶）。
- **登录/注册弹窗**：全局可唤起，含「登录」「注册」双 Tab。

## 8. 业务规则

### 8.1 产品规则

产品字段：`id`、`slug`、保险名、一句话卖点、类别、年保费、保额、保障期限、服务内容列表、适用车型、标签、排序权重、是否上架。语言无关字段（价格、保额、排序等）单独存放，见 §10.3。

**本期 mock 产品清单（6 款）**

| slug | 保险名 | 类别 | 年保费 | 保额 | 标签 |
| --- | --- | --- | --- | --- | --- |
| `compulsory-traffic` | 交强险 | 法定必投 | ¥950 | ¥200,000 | 法定 |
| `commercial-basic` | 商业险 · 基础版 | 商业险套餐 | ¥1,280 | ¥500,000 | — |
| `commercial-comfort` | 商业险 · 畅行版 | 商业险套餐 | ¥2,680 | ¥1,000,000 | 热销 |
| `commercial-premium` | 商业险 · 尊享版 | 商业险套餐 | ¥4,580 | ¥2,000,000 | 新品 |
| `third-party-liability` | 第三者责任险 | 单险种 | ¥1,150 | ¥1,000,000 | — |
| `own-damage` | 车损险 | 单险种 | ¥1,860 | 按车辆实际价值 | — |

- 价格统一为**年保费**，币种人民币 CNY，展示形如 `¥2,680 / 年`。
- 每个产品必须至少 3 条服务内容，否则不展示。
- 产品下架（`active=false`）时，列表与首页分区均不展示，直链访问返回 404。
- 产品数据的唯一来源是后端 mock JSON，前端组件不得内联硬编码产品信息。

### 8.2 价格与订单规则

- 订单金额 = 所选产品当前价格，本期无折扣、无附加险加价、无税费叠加。
- 订单号用 UUID（v4）生成（`crypto.randomUUID()`），全站唯一。**订单号即订单标识 `id`**，不另设 `orderNo` 字段，也不维护编号自增序列。
- 下单时快照产品名与价格，后续产品改价不影响历史订单。
- 订单状态机：`待支付(PENDING)` → `已生效(ACTIVE)`；`待支付` 可 `取消(CANCELLED)`；`已生效` 到期后为 `已失效(EXPIRED)`。
- 本期无真实支付：个人中心订单详情提供「模拟支付」入口，调用后订单由 `待支付` 转为 `已生效`。
- 同一用户可拥有多个订单；同一车辆同一产品在 `待支付/已生效` 状态下不可重复下单。
- 仅订单归属人可查看、取消或支付自己的订单。

### 8.3 账户规则

- 注册字段：用户名（2–20 字符，允许中英文与数字）、邮箱（唯一，需符合邮箱格式）、密码。
- 密码规则：长度 ≥ 8，且同时包含字母与数字。
- 登录方式：邮箱 + 密码。
- 密码在服务端哈希存储，任何接口响应不得返回密码或其哈希。
- 邮箱已存在时注册失败并内联提示「该邮箱已注册」。
- 登录失败统一提示「邮箱或密码错误」，不区分具体原因。
- 鉴权方式：登录成功后签发 HttpOnly Cookie 会话（`swi_session`）。
- **会话有效期 1 小时（滑动续期）**：Cookie `maxAge=3600`，服务端会话记录同步 1 小时有效期；每次通过会话校验的请求都把有效期顺延为「当前时间 + 1 小时」，持续操作时登录态不会中途失效。
- **不设绝对上限**：持续有请求则登录态一直顺延；只有主动退出或空闲超过 1 小时才失效。
- **到期交互**：接口返回未授权 → 前端清除登录态并唤起登录弹窗 → 登录成功后回到当前页面。
- **实现注意**：续期需要重写 Cookie，只能在 Route Handler、Server Action 或中间件中完成；Server Component 渲染路径不承担续期。
- 未登录访问需登录页面时，先打开登录弹窗，登录成功后回到原意图页面。
- 不做短信/邮箱验证码，不做第三方登录。

**修改资料规则**

- 可修改字段：用户名、邮箱（两者均可改）。
- 邮箱修改需通过唯一性校验，且需符合邮箱格式。
- 保存成功后，Header 与个人中心展示的用户名同步更新。

**修改密码规则**

- 需先输入当前密码，校验通过才允许修改。
- 新密码规则同注册；新密码不得与当前密码相同。
- 修改成功后，作废该用户的其它会话，当前会话保留，并提示成功。

### 8.4 导航与滚动规则

- 全站使用 Next.js App Router 真实路由，**不使用 hash 路由**（禁止 `#/xxx` 形式路由，也不依赖 URL 片段做定位）。
- 首页五个分区的锚点顺序与 Header Tab 顺序严格一致：首页 → 保险产品 → 投保指引 → 投保案例 → 关于我们。
- 在首页点击 Tab：页面平滑滚动到对应分区，不改变 URL、不刷新页面。
- 在其他页面点击 Tab：先路由到该语言的首页，再平滑滚动到对应分区；滚动意图通过 `sessionStorage` 传递，避免在 URL 中留下 hash 或查询参数。
- 手动滚动时，当前可视分区对应的 Tab 高亮跟随（基于 IntersectionObserver）。
- Header 吸顶；移动端（< 1024px）导航收纳为抽屉菜单，点击项后自动收起。

### 8.5 语言规则

- 语言集合：`zh`（中文，默认）、`en`（英文），作为 URL 第一段。
- 采用 Next.js 官方 i18n 方案：`app/[locale]/` 路由段 + JSON 字典 + 中间件，不引入第三方 i18n 库。
- 根路径 `/` 由中间件按「语言 Cookie → 浏览器 `Accept-Language` → 默认 `zh`」的顺序重定向到 `/zh` 或 `/en`。
- 语言段非法（非 `zh`/`en`）时返回 404。
- 切换语言：保持同一页面路径，仅替换语言段并跳转；首页场景下用 `sessionStorage` 复原所在分区位置。
- 语言偏好写入 Cookie（有效期 1 年），用于根路径重定向。
- 页面 `html lang` 随语言切换；两种语言 URL 一一对应，输出 `hreflang` 备用链接。
- 产品名、服务内容等后端 mock 数据同样双语，按语言返回对应字段；服务端渲染时以 URL 语言段为准，接口以 `?locale=` 或 `Accept-Language` 兜底。

### 8.6 响应式规则

- 断点：移动端 `< 768px`、平板 `768–1023px`、桌面 `>= 1024px`。
- 产品列表：桌面 3 列、平板 2 列、移动端 1 列。
- 投保表单：桌面双列、移动端单列。
- 个人中心：桌面左侧边栏 + 右侧内容区；移动端顶部横向 Tab + 内容区。
- 全站最小支持宽度 360px，无横向滚动条。

## 10. API / 数据需求

### 10.1 统一响应体与接口一览

**统一响应体**：所有接口返回同一结构，前端只需实现一套解析与错误处理。

```ts
type ApiResponse<T> = {
  success: boolean;        // 是否成功，true / false
  code: ApiCode;           // 业务码，成功为字符串 "OK"
  message: string;         // 面向开发者与兜底的提示文案，UI 不作为文案来源
  data: T | null;          // 业务数据；成功时返回对象或列表，失败为 null
};

type ApiCode = string;     // 取值见下方业务码表
```

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `success` | boolean | 是否成功。前端以此判断，不用 HTTP 状态码猜 |
| `code` | string | 业务码。**统一为字符串**，不用数字（见下方说明） |
| `message` | string | 兜底文案。**UI 的文案来源是 `code` 查字典，不是这个字段**（见下方说明） |
| `data` | `T \| null` | 成功返回数据，失败固定为 `null`，保证结构稳定 |

**为什么 `code` 只用字符串，不做 `number | string`**
数字码需要额外维护一份「码 → 含义」的对照表，且容易在不同模块间撞号；字符串码自解释、可 grep、加新码不必排队领号。`VALIDATION_ERROR` 比 `4001` 更省沟通成本，代价只是长几个字节。

**为什么 `message` 不能当作 UI 文案**
本站是中英双语。若界面直接渲染后端返回的 `message`，英文用户会看到中文提示。正确链路是：后端返回 `code` → 前端用 `code` 在 `zh.json` / `en.json` 的 `errors` 命名空间下取文案 → 渲染。`message` 保留给开发者看日志、以及前端字典里没有该码时的兜底。

**HTTP 状态码同样要正确设置**，不能一律返回 200：

| 场景 | HTTP 状态码 |
| --- | --- |
| 查询成功 | 200 |
| 创建成功 | 201 |
| 字段校验失败 | 400 |
| 未登录或会话过期 | 401 |
| 无权访问他人资源 | 403 |
| 资源不存在 | 404 |
| 邮箱已存在、重复下单、订单状态不允许取消 | 409 |
| 服务端异常 | 500 |

| 方法 | 路径 | 说明 | 鉴权 |
| --- | --- | --- | --- |
| GET | `/api/products` | 产品列表；可选 `?locale=zh\|en`，缺省按 `Accept-Language` | 否 |
| GET | `/api/products/[slug]` | 产品详情，同上语言规则 | 否 |
| GET | `/api/guide` | 投保指引内容（步骤/材料/FAQ） | 否 |
| GET | `/api/cases` | 投保案例列表（10 条演示案例） | 否 |
| POST | `/api/auth/register` | 注册：`{ username, email, password }` | 否 |
| POST | `/api/auth/login` | 登录：`{ email, password }` | 否 |
| POST | `/api/auth/logout` | 退出登录，清除会话 | 是 |
| GET | `/api/auth/session` | 获取当前登录用户 | 否 |
| PATCH | `/api/auth/profile` | 修改资料：`{ username, email }` | 是 |
| POST | `/api/auth/password` | 修改密码：`{ currentPassword, newPassword }` | 是 |
| GET | `/api/orders` | 我的订单列表，支持 `?status=` 筛选 | 是 |
| POST | `/api/orders` | 创建订单（提交投保） | 是 |
| GET | `/api/orders/[id]` | 订单详情 | 是 |
| POST | `/api/orders/[id]/cancel` | 取消订单 | 是 |
| POST | `/api/orders/[id]/pay` | 模拟支付成功，订单转为已生效 | 是 |
| POST | `/api/chat` | 客服对话，流式返回；**响应体是 AI SDK 的 UI 消息流，不套统一信封** | 否（登录态影响订单工具，见 §10.4） |
| GET | `/api/chat` | 按 `?sessionId=` 取该会话的聊天记录，走统一信封 | 否 |

**业务码表（`code` 字段取值）**

| 业务码 | HTTP | 触发场景 | 失败时贴到哪个位置 |
| --- | --- | --- | --- |
| `OK` | 200 / 201 | 成功 | — |
| `VALIDATION_ERROR` | 400 | 请求字段不合法（服务端兜底，见下方说明） | 表单级 `Alert` |
| `UNAUTHORIZED` | 401 | 未登录、会话过期 | 弹登录框 |
| `FORBIDDEN` | 403 | 访问不属于自己的订单 | 页面级 404 |
| `NOT_FOUND` | 404 | 产品 / 订单不存在，或产品已下架 | 页面级 404 |
| `EMAIL_TAKEN` | 409 | 注册或修改资料时邮箱已被占用 | 邮箱字段 |
| `DUPLICATE_ORDER` | 409 | 同车同产品已存在待支付或已生效订单 | 表单级 `Alert` |
| `ORDER_NOT_CANCELLABLE` | 409 | 对非「待支付」订单执行取消 | `sonner` toast |
| `INVALID_CREDENTIALS` | 400 | 登录时邮箱或密码错误 | 表单级 `Alert` |
| `INVALID_PASSWORD` | 400 | 修改密码时当前密码不正确 | 当前密码字段 |
| `SAME_PASSWORD` | 400 | 新密码与当前密码相同 | 新密码字段 |
| `TOO_WEAK` | 400 | 新密码少于 8 位或缺少字母 / 数字 | 新密码字段 |
| `INTERNAL_ERROR` | 500 | 未预期的服务端异常 | 表单级 `Alert` |

**字段级校验由前端负责**

服务端不返回字段级错误明细，分工如下：

- **前端**用 zod 完成字段级校验：必填、格式、长度、两次输入一致、密码强度。文案走字典，错误贴在字段下方。绝大多数非法输入在发请求前就被拦住。
- **服务端**仍然重复校验（不能信任客户端），失败时返回 `VALIDATION_ERROR`，前端以**表单级 `Alert`** 呈现，不指向具体字段。
- 能唯一对应到某个字段的业务码（`EMAIL_TAKEN`、`INVALID_PASSWORD`、`SAME_PASSWORD`、`TOO_WEAK`）按上表直接贴到该字段，不需要额外的字段级结构。

**已知取舍**：当客户端校验被绕过、且服务端校验失败时，用户看到的是表单级提示而非字段级提示。由于前后端共用同一份 zod schema（见 `ui-patterns.md` §2 的 `lib/validation/`），正常操作路径下不会触发。

### 10.2 数据模型

**Product（语言无关部分）**：`id`、`slug`、`category`、`price`、`coverageAmount`、`period`、`badge`、`active`、`sortOrder`。

**Product（语言相关部分）**：`slug`、`name`、`tagline`、`applicableVehicles`、`coverages[]`（`title`、`desc`）。

**User**：`id`、`username`、`email`、`passwordHash`、`createdAt`、`updatedAt`。

**Session**：`id`、`userId`、`expiresAt`（签发后 1 小时）。

**Order**：`id`（UUID v4，同时作为展示用订单号）、`userId`、`productId`、`productSnapshot { nameZh, nameEn, price }`、`insured { name, idNo, phone }`、`vehicle { plateNo, brandModel, vin, registerYear }`、`amount`、`status`、`createdAt`、`effectiveAt`、`expireAt`。

**Guide**：`steps[]`（标题 + 说明 + 时长）、`materials[]`（材料名 + 说明 + 是否必需）、`faqs[]`（问题 + 答案）。

**Case**：`id`、`sortOrder`、`productId`、`icon`、`claimDays`、`plateNo` 为语言无关字段；`city`、`ownerName`、`summary`、`quote` 按语言取值。卡片上的产品名不单独翻译，由 `productId` 关联产品数据按当前语言取，避免产品改名后案例里的名字不同步。

**ChatSession**：`id`、`userId`（登录后写入，未登录保持 `null`）、`messages[]`、`updatedAt`；存于 Upstash Redis 并带 7 天 TTL，规则见 §10.4。

### 10.3 数据文件与存储

**字典（界面文案）**：`lib/i18n/dictionaries/zh.json`、`en.json`，按模块分键（`nav`、`home`、`products`、`guide`、`cases`、`about`、`auth`、`account`、`common`、`errors`）。

**产品与指引 mock 数据**：拆成「语言无关 + 语言相关」两组 JSON，按 `slug` 合并。

```
lib/mock/products/
├── base.json   # id、slug、category、price、coverageAmount、period、badge、active、sortOrder
├── zh.json     # slug、name、tagline、applicableVehicles、coverages
└── en.json
```

- 选择拆分而非在 `zh.json` / `en.json` 里各自复制一份价格，是为了让价格只有一处定义，避免两份文件改价不同步。
- 读取时按 `slug` 合并 `base` 与对应语言文件；加载时校验两份语言文件的 `slug` 集合与 `base` 完全一致，不一致直接抛错。
- `guide/` 目录采用同样结构（`base.json` + `zh.json` + `en.json`）。
- `cases/` 目录同样拆成三份：`base.json` 按 `id` 存语言无关字段，`zh.json` / `en.json` 按 `id` 存城市、车主、摘要与原话；加载时校验两份语言文件的 `id` 集合与 `base` 完全一致，并校验 `productId` 能在产品数据里找到。

**存储（Upstash Redis）**：用户、会话、订单、客服聊天记录存放在 Upstash Redis（`lib/server/redis.ts` 建客户端与键名，`lib/server/store.ts` 做数据访问）。选 Redis 而不是继续用进程内存，是因为 Vercel 上每个 Route Handler 都是独立函数实例，进程内存无法跨实例共享——登录写入实例 A、下一次请求落到实例 B 就会读不到会话。

| 数据 | Redis 键 | 结构 | TTL |
| --- | --- | --- | --- |
| 用户 | `swi:user:<userId>` | JSON | 常驻 |
| 邮箱唯一索引 | `swi:email:<email 小写>` | userId 字符串 | 常驻 |
| 会话 | `swi:session:<sessionId>` | `{ id, userId, expiresAt }` | 1 小时，滑动续期 |
| 用户会话索引 | `swi:usessions:<userId>` | Set（sessionId 集合） | 常驻，登出 / 改密时同步 |
| 订单 | `swi:order:<orderId>` | JSON | 常驻 |
| 用户订单列表 | `swi:uorders:<userId>` | List（orderId，`LPUSH` 倒序） | 常驻 |
| 重复投保索引 | `swi:dedup:<userId>:<车牌大写>:<productId>` | orderId 字符串 | 常驻 |
| 客服会话 | `swi:chat:<sessionId>` | `{ id, userId, messages, updatedAt }` | 7 天 |

- 所有键统一 `swi:` 前缀，可安全复用同一个 Upstash 实例。
- 连接信息从环境变量读取，优先 `swi_KV_REST_API_URL` / `swi_KV_REST_API_TOKEN`，其次兼容无前缀的 `KV_REST_API_URL`、`KV_REST_API_TOKEN`、`UPSTASH_REDIS_REST_URL` 等；客户端懒加载，缺配置时在首次调用处报错，而不是构建期崩溃。
- 邮箱唯一性用 `SETNX` 原子抢占（`swi:email:`），并发注册同一邮箱只有一个实例能成功，比「先查后写」稳。
- 订单状态变更（支付、取消、到期结算）必须显式回写（`saveOrder`）；不能再依赖改对象引用，因为读出来的只是反序列化副本。

**初始化种子数据**：1 个演示账号（`demo@example.com` / `Demo1234`）与 2 条不同状态的演示订单，用 `SETNX` 幂等写入——多实例并发启动只会写一份，且只写不覆盖，不会冲掉用户后来注册或下单的数据。

**访问控制**：用户、订单、账户维护接口均需通过会话校验，禁止仅凭 `userId` 参数读取或修改他人数据。

### 10.4 在线客服（AI 对话）

首页悬浮工具轨的「在线客服」是一个 AI 客服助手，负责产品解答、投保指引答疑与订单查询。

**技术构成**：前端对话组件用 AI Elements（`components/ai-elements/` 的 `Conversation` / `Message` / `PromptInput`，源码入库可改）；后端用 AI SDK 的 `ToolLoopAgent` 驱动，工具参数用 zod 约束；消息经 `POST /api/chat` 流式返回。

**凭据与模型配置**：模型走 OpenAI 兼容接口（`@ai-sdk/openai-compatible` 的 `createOpenAICompatible`），四项配置全部从环境变量读取，仓库只提交模板文件 `.example.env`：

| 变量 | 说明 |
| --- | --- |
| `AI_PROVIDER_NAME` | 提供方名称，仅用于标识与日志 |
| `AI_BASE_URL` | 接口地址，需带 `/v1` 这类版本前缀 |
| `AI_API_KEY` | 接口密钥 |
| `AI_MODEL` | 模型 id |

任一项缺失时接口直接返回 `INTERNAL_ERROR`，并提示去 `.example.env` 补配置。`.gitignore` 已忽略 `.env*`，真实密钥不入库。

**工具（tools）**

| 工具 | 参数（zod 约束） | 行为 |
| --- | --- | --- |
| `searchProducts` | `keyword?`、`category?`、`maxPrice?` | 查询产品数据，返回名称、价格、保额、保障内容、适用车型，最多 6 条 |
| `queryOrders` | `userId` | 按 `userId` 查询 Redis 中的真实订单，最多 10 条 |

**业务规则**

- **产品问题**：必须先调用 `searchProducts`，禁止凭记忆编造价格或保障内容；**未登录也能咨询产品**。
- **订单问题**：必须先调用 `queryOrders`。传入的 `userId` 与服务端会话解析出的用户不一致或为空时，工具返回 `requiresLogin`，助手只提示「请先注册登录」，不返回任何订单信息。
- **登录态判定**：一律由服务端读取 Cookie 会话，前端传参不参与判定，「请先登录」这道门无法从前端绕过。
- **会话记录**：浏览器生成会话 id 存 localStorage，服务端用 Redis 维护「会话 id → 消息列表」（`swi:chat:<sessionId>`，7 天 TTL）；**登录后发消息即把该会话绑定到 `userId`**，已绑定的会话只回给本人。单会话只保留最近 60 条消息。
- **回答语言**：跟随页面语言（`zh` / `en`），与 URL 语言段一致。
- **输入形态**：仅支持文本，不接受图片、文件、语音。
- **范围外问题**：不编造，引导用户通过页脚的电话或邮箱联系人工客服。

## 11. 约束

- **技术约束**：Next.js 全栈；产品与指引数据由后端 mock JSON 提供，前端经接口请求获取。
- **存储约束**：账户 / 会话 / 订单 / 客服聊天记录存 Upstash Redis，可在多实例与 Serverless 环境下共享；会话有效期 1 小时并滑动续期，聊天记录 7 天过期。产品、指引、案例仍为构建期只读 mock JSON，不进 Redis。
- **路由约束**：不使用 hash 路由；URL 首段必须为语言（`zh` / `en`）。
- **UI 约束**：优先使用 shadcn/ui 组件与 Tailwind 原子类，避免自造基础组件；新增组件用 `npx shadcn@latest add <name>` 安装；视觉规范详见 `visual.md` / `design.md`。
- **数据约束**：全部为 mock 数据，不得冒充真实保险条款；页面需明示「演示数据」。
- **合规约束**：公司名称、地址、电话、备案号等均为占位内容，不得展示真实保险公司名称、牌照号或真实费率表。
- **品牌约束**：站名「汽车保险」；Logo 使用项目自带 `public/next.svg`。
- **素材约束**：首屏背景视频 `public/hall.mp4`（1280×720 / 24fps / 10s / 4.9MB），poster `public/hall-poster.jpg`（1280×720，取视频第 0.15s 帧）；微信二维码 `public/wx.jpg`。
- **视觉方向**：走「专业可信」路数——深蓝主色 + 少量暖色点缀；具体色值、字体、阴影在 `design.md` 定义。
- **性能约束**：列表使用稳定 key；图片懒加载；避免首屏过量动画。
- **首屏媒体约束**：4.9MB 的 `hall.mp4` 不得参与 LCP——poster 用 `next/image` 的 `priority` 先上，视频等窗口 `load` 之后才挂载并淡入；滑出视口暂停解码；`prefers-reduced-motion: reduce` 时不加载视频。详见 `avoid.md` §5。
- **客服约束**：在线客服为 AI 助手，只接受文本输入，不接受图片 / 文件 / 语音；模型凭据只从环境变量读取，仓库仅提交 `.example.env` 模板。
- **无障碍约束**：导航、弹窗、表单、侧边栏 Tab 具备键盘可达性与 ARIA 语义。

**非目标（本期不做）**

- 真实支付、真实保单、理赔、续保提醒、短信/邮件通知、第三方登录、优惠券、代理人体系、运营后台、PDF 保单导出、关系型数据库（状态数据存 Redis，不做关系建模）。
