# prd.md：做什么

**回答**：做什么、给谁做、做到什么程度、边界在哪。
**不回答**：长什么样（visual.md）、令牌与像素（design.md）、怎么搭（ui-patterns.md）、每页细节（page-specs.md）。

## 骨架

```markdown
# <产品名> PRD

> 版本：v0.1｜日期：YYYY-MM-DD｜上游：无｜下游：visual.md / design.md / ui-patterns.md / page-specs.md

## 1. 产品定位
## 2. 目标用户与使用场景
## 3. 用户问题
## 4. 核心场景
## 5. 功能清单
## 6. 用户流程
## 7. 页面与功能列表
## 8. 业务规则
## 9. 技术栈与约束
## 10. API 一览
## 11. 统一响应体契约
## 12. 业务码与错误映射
## 13. 数据模型
## 14. 数据来源与 mock 约定
## 15. 非目标
## 16. 待确认

```

## 每节写什么

- **1 定位**：一句话说清做什么、给谁、解决什么，再补一段「不做什么」。
- **2 目标用户**：1–3 类角色，各自的使用设备、频率、环境。
- **3 用户问题**：现在他们怎么凑合（竞品、Excel、纸质、电话），痛点具体到动作。
- **4 核心场景**：编号走查，每条写清起点 → 动作 → 成功结果 → 失败结果。
- **5 功能清单**：`F1…Fn`，每条含 **做什么 / 输入 / 输出 / 规则 / 异常**。
  功能是**可验收单元**（「改邮箱」「模拟支付成功」），不是模块名（「账户模块」）。
- **6 用户流程**：关键路径分步，必须覆盖未登录、失败、中断三种分支。
- **7 页面与功能列表**：表格 `Route | 页面 | 承载功能 | 是否需要登录 | 入口`。
  Route 写成最终形态（含 i18n 前缀、动态段），不要写「待定」。
- **8 业务规则**：校验规则、限额、时效；状态机要写全 **状态 → 合法迁移 → 触发条件 → 谁能触发**。
- **9 技术栈与约束**：框架与版本、包管理器、路由形态（是否 hash）、渲染与部署形态、
  不允许引入的依赖、浏览器与设备支持范围。任何本清单之外的新技术栈，先问用户再引入。
- **10 API 一览**：`方法 | 路径 | 鉴权 | 用途 | 成功 | 失败`。一次定全，别等编码时再长出来。
- **11 统一响应体契约**：如 `success / data / code / message`，写清成功与失败时各字段的形态，
  并指定它放在哪个共享目录，让前后端共用同一份类型定义。只保留真正需要的字段。
- **12 业务码与错误映射**：`码 | HTTP | 含义 | 呈现位置`。
  原则：能唯一归属到某个字段的码贴到那个字段，其余集中呈现为表单级或全局提示。
- **13 数据模型**：每个实体一段，字段、类型、必填、唯一、默认值、生成规则（如订单号用 uuid 还是业务编号）。
- **14 数据来源与 mock 约定**：数据存哪（内存 / 文件 / 数据库）；mock 文件怎么分（按实体、按语言）；
  启动时怎么校验（如多语言文件的 id 集合必须与基准一致）。
- **15 非目标**：这次明确不做的 3–8 条。
- **16 待确认**：把散落各处的「假设：…」集中列一遍，供用户一次性拍板。
- **17 变更记录**：日期 + 改了什么 + 为什么。

## 写作要点

- 顺序建议：先跟用户对齐 1–4 和 15，再展开 5–14。范围没定就写接口，返工是必然的。
- 每个数字都要有出处（谁定的、依据什么）；没有依据的写「待确认」。
- 引用其它文档只写「见 design.md §3」，不要把内容抄过来。

## 常见漏项（写完自查）

- 只写正常路径，没写重复提交、未登录、会话过期、数据不存在、并发。
- 状态名有了，但没写谁能把状态改成谁。
- 没写「谁看到什么」：未登录 / 已登录 / 访问他人资源。
- 接口和数据模型各写一半，字段对不上。
- 编号、金额、时长、时效的格式没定规则，前后端各写一套。
- 用户给的原始清单被改名、合并或漏抄。
- 非目标空着，范围必然蔓延。

## 验收清单

- [ ] 外人只看这份文档就能复述产品做什么、给谁做。
- [ ] 每个功能都有编号，且能对应到至少一个页面或接口。
- [ ] 所有 Route 都在表里，且标注了鉴权要求。
- [ ] 每个业务码都有明确的呈现位置。
- [ ] 数据模型的每个字段都能在功能或页面里找到来源。
- [ ] 非目标与待确认都非空。
