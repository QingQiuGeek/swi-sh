# 执行与验收：AI Coding、按模块验收、整体验收

进入 build / accept 模式时读这份。

## 1. 执行纪律

- **先读后改**：动手前通读相关代码与对应文档，理解现有约定再改。
- **一次一个模块**：不把多个模块塞进一次改动，否则出问题无法归因。
- **只改必须改的**：每行改动都要能追溯到本次需求；不顺手重构无关代码、不改格式、不动无关文件。
- **不做需求外的功能、抽象、配置**。
- **新技术栈先问**：要引入未被声明的框架、库、外部服务时，先问用户再引入。
- **用原生写文件工具**编辑文件。不要用 shell here-string / 字符串拼接生成多行文件内容，
  容易出现字面转义符并把标题、锚点写坏；改动后 `grep` 一下标题与关键锚点确认完好。
- **静态检查自己跑**：类型检查、lint 必须自己跑通过再交付，不要留给用户发现。
- **失败先复现**：报 bug 时先写一个能稳定复现的最小场景，再改。

### 改完自检（按改动类型选做）

- 改动涉及 UI：用真实浏览器打开，走一遍主路径；每个断点至少看一次；控制台无报错。
- 改动涉及接口：先直接请求接口确认返回体形态，再看前端。
- 改动涉及数据：确认所有语言的 mock 文件 id 集合一致、字段名一致。
- 改动涉及行为：同步回写对应文档（见 SKILL.md 变更回写表）。
- 改动涉及文案：多语言字典同时补齐，检查是否残留旧键或旧文案。

## 2. 按模块验收

**每完成一个模块/功能，先让用户验收，通过后再进入下一个。** 不要一口气做完再交付。

交付说明包含四件事：

1. **改了什么**：文件路径 + 一句话说明。
2. **怎么验**：用户能直接执行的步骤或入口（页面路径、命令、账号）。
3. **证据**：可复核的量化证据——命令输出、测量数值、截图、帧率/耗时等。
   不要只说「已优化」「很流畅」「应该没问题」。
4. **已知限制**：没做到的、有取舍的、需要用户决策的，明确写出来。

验收不通过时：先复现用户描述的现象，定位根因再改，不要凭猜测打补丁。

## 3. 最终整体验收

全部模块做完后，做一次以文档为基准的整体核对：

- **逐条对照**：prd.md 的每个功能、page-specs.md 的每页、ui-patterns.md 的每条规范，
  都能在代码里找到对应实现；对不上的要么改代码，要么改文档（并说明为什么）。
- **关键路径走查**：未登录 → 登录 → 核心操作 → 失败分支 → 退出，全流程走一遍。
- **全局一致性**：术语、文案、颜色、间距、组件用法、错误提示位置。
- **响应式与可访问性**：全部断点、键盘可达、焦点可见、对比度达标。
- **文档与代码同步**：六份文档反映的是当前实现，不是某个早期版本。

输出格式：

```text
通过项：…
不通过项：…（含复现步骤与影响）
已知取舍：…（为什么这样选）
```

## 4. 停止条件

- 用户验收通过并明确说「继续下一个」，才进入下一个模块。
- 用户没要求时，不要一次改多个模块，也不要顺手做「顺便优化」。
- 发现需求外的缺陷：报告它，不要默默修（除非用户同意）。
